# v3.10.2

## State 自动维护调度修复

- 修复维护探测把共享账号总并发写死为 1 的问题。采集和验证均读取账号实际并发限制；账号未设置时使用当前全局默认值，同时遵守全局请求间隔。账号配置 10 个并发、只有 1 个业务请求时，不再因此阻止维护。
- 业务与维护继续共用账号总容量，不绕过并发限制。维护自身保留全局探测并发上限，每个调度周期同一账号最多安排一个模型任务，采集与验证之间仍保留维护专用等待。
- 调度存储不可用与账号容量／请求间隔等待分别提示。未取得调度租约时，不消耗维护请求预算。
- 修复真实业务活跃时间在运行时锁繁忙时被直接丢弃的问题。活跃时间按账号和精确模型合并，持久化 CAS 成功后才确认，跨实例同步不会直接覆盖待写活动。
- 活跃时间重放不恢复旧开关、已撤销候选或已删除的旧自动维护项。缓冲有界且位于内存，进程崩溃前尚未提交的活动仍可能丢失。

## 候选诊断

- 将笼统的“无符合结构、长度和剩余时间要求的新 state”拆分为：上游未返回、结构无法解析、长度／块数不匹配、签发时间超前、估算剩余时间不足、已有重复值。
- 长度和时间相关诊断显示实际字符数、密文块数及按配置 TTL 估算的剩余秒数，并保留在诊断历史中，不回显 State 原文。
- 维护请求正常完成但候选未入选时，使用统计保留真实成功结果及 token 用量，并记录未入选原因；请求成功不等于候选成功发布。
- 默认候选形态仍为 292 字符／10 块与 332 字符／12 块，不自动放行 312；自定义规则继续生效。长度不代表模型能力，估算 TTL 不是上游有效期保证。

## 账号模型选择

- “账号与模型”选择账号后自动加载该账号模型目录，支持搜索、多选和批量添加维护项，无需手填模型名。
- 支持手动从上游刷新模型；按账号模型白名单／黑名单过滤，排除图片模型和重复维护项。
- 切换账号清空旧选择，忽略旧请求的迟到结果；加载失败时明确提示，不串用其他账号的模型。
- 模型目录只代表已发现模型，不保证即时额度或每次上游调用均可用。
